## Welcome Contributors!

This guide helps you contribute to container-use. Whether you're fixing bugs, adding features, or improving documentation, this guide will get you started.

## Prerequisites

Before you begin, make sure you have:

- **Go 1.21+** - [Install Go](https://go.dev/doc/install)
- **Docker** - [Install Docker](https://docs.docker.com/get-docker/)
- **Git** - Should be installed on most systems
- **Make** (optional) - For convenience commands

## Getting Started

### 1. Fork and Clone

```bash
# Fork the repository on GitHub, then:
git clone https://github.com/YOUR-USERNAME/container-use.git
cd container-use
```

### 2. Install Dependencies

```bash
go mod download
```

### 3. Build

```bash
# Build the binary
go build -o container-use ./cmd/container-use

# Or use Dagger
dagger call build --platform=current export --path ./container-use
```

### 4. Run Tests

```bash
# Run all tests (unit + integration)
go test ./...

# Run only unit tests (fast)
go test -short ./...

# Run specific package tests
go test ./environment
go test ./repository
go test ./mcpserver

# Run with verbose output
go test -v ./...

# Run integration tests only (requires Docker)
go test -count=1 -v ./environment/integration
```

### 5. Format Code

**Always format before committing:**

```bash
go fmt ./...
```

### 6. Lint

```bash
# Using Dagger
dagger call lint

# Or install golangci-lint locally
golangci-lint run
```

## Development Workflow

### Making Changes

1. **Create a feature branch:**
```bash
git checkout -b feature/your-feature-name
```

2. **Make your changes**

3. **Test your changes:**
```bash
go test -short ./...  # Unit tests
go test ./...         # All tests
go fmt ./...          # Format
```

4. **Commit your changes:**
```bash
git add .
git commit -m "feat: add new feature"
```

Use [Conventional Commits](https://www.conventionalcommits.org/):
- `feat:` - New feature
- `fix:` - Bug fix
- `docs:` - Documentation changes
- `test:` - Test changes
- `refactor:` - Code refactoring
- `chore:` - Maintenance tasks

5. **Push and create PR:**
```bash
git push origin feature/your-feature-name
```

### Testing Your Changes

#### Manual Testing with stdio

**IMPORTANT:** You cannot test container-use in its own `/workdir`. Always test in a separate repository.

```bash
# Create a test repository
mkdir /tmp/test-repo
cd /tmp/test-repo
git init
touch README.md
git add README.md
git commit -m "initial commit"

# Test the stdio interface
echo '{"jsonrpc":"2.0","method":"ping","id":1}' | /path/to/container-use stdio

# Test listing tools
echo '{"jsonrpc":"2.0","method":"tools/list","id":1}' | /path/to/container-use stdio | jq

# Test environment creation
printf '{"jsonrpc":"2.0","method":"tools/call","params":{"name":"environment_create","arguments":{"environment_source":"/tmp/test-repo","title":"Test Environment"}},"id":1}' | /path/to/container-use stdio | jq
```

#### Testing with a Real Agent

1. Build your local version:
```bash
go build -o /tmp/container-use-dev ./cmd/container-use
```

2. Configure your agent to use the dev binary:
```bash
# For Claude Code
claude mcp add container-use-dev -- /tmp/container-use-dev stdio

# Test it
cd /tmp/test-repo
claude "Create a hello world app"
```

3. Check logs:
```bash
# Enable debug output
/tmp/container-use-dev --debug stdio
```

## Common Development Tasks

### Adding a New MCP Tool

1. **Define the tool in `mcpserver/tools.go`:**

```go
func createMyNewTool(singleTenant bool) *Tool {
    return &Tool{
        Definition: newEnvironmentTool(
            envToolOptions{
                name:                  "environment_my_operation",
                description:           "Description of what this does",
                useCurrentEnvironment: singleTenant,
            },
            mcp.WithString("my_param",
                mcp.Description("Description of parameter"),
                mcp.Required(),
            ),
        ),
        Handler: func(ctx context.Context, request mcp.CallToolRequest) (*mcp.CallToolResult, error) {
            repo, env, err := openEnvironment(ctx, request)
            if err != nil {
                return nil, err
            }

            myParam, err := request.RequireString("my_param")
            if err != nil {
                return nil, err
            }

            // Implement your operation
            result, err := env.MyOperation(ctx, myParam)
            if err != nil {
                return nil, err
            }

            // Persist changes
            if err := repo.Update(ctx, env, "My operation completed"); err != nil {
                return nil, err
            }

            return mcp.NewToolResultText(result), nil
        },
    }
}
```

2. **Add to `createTools()` in `mcpserver/tools.go`:**

```go
func createTools(singleTenant bool) []*Tool {
    return []*Tool{
        // ... existing tools
        createMyNewTool(singleTenant),
    }
}
```

3. **Implement the operation in `environment/environment.go`:**

```go
func (env *Environment) MyOperation(ctx context.Context, param string) (string, error) {
    // Implementation
    container := env.container()
    
    // Do something with the container
    container = container.WithExec([]string{"sh", "-c", param})
    
    // Update environment state
    if err := env.apply(ctx, container); err != nil {
        return "", err
    }
    
    return "success", nil
}
```

4. **Write tests:**

```go
func TestMyOperation(t *testing.T) {
    // Test implementation
}
```

## Code Style Guidelines

### Go Code

- Follow standard Go conventions
- Use `gofmt` (enforced)
- Write clear, self-documenting code
- Add comments for complex logic
- Keep functions small and focused

**Good:**
```go
// calculateEnvID generates a unique environment identifier
func calculateEnvID() string {
    return petname.Generate(2, "-")
}
```

**Bad:**
```go
// This function does stuff
func doStuff(x interface{}) interface{} {
    // Complex logic without explanation
}
```

### Error Handling

- Always check errors
- Provide context in error messages
- Use `fmt.Errorf` with `%w` for wrapping

**Good:**
```go
if err := repo.Create(ctx, dag, title, "", "HEAD"); err != nil {
    return fmt.Errorf("failed to create environment: %w", err)
}
```

**Bad:**
```go
repo.Create(ctx, dag, title, "", "HEAD")  // ignoring error
```

### Testing

- Write tests for new features
- Maintain test coverage
- Use table-driven tests for multiple cases
- Use `testing.Short()` to separate unit/integration tests

```go
func TestMyFeature(t *testing.T) {
    tests := []struct{
        name string
        input string
        want string
    }{
        {"case1", "input1", "output1"},
        {"case2", "input2", "output2"},
    }
    
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got := MyFeature(tt.input)
            if got != tt.want {
                t.Errorf("got %v, want %v", got, tt.want)
            }
        })
    }
}
```

## Common Gotchas

### 1. Git Repository Context

Always test in a proper Git repository, not in `/workdir`:
```bash
# BAD - testing in container-use's own directory
cd /workdir && echo '...' | container-use stdio

# GOOD - testing in a separate repo
cd /tmp/test-repo && echo '...' | /path/to/container-use stdio
```

### 2. Dagger Context

Integration tests need a Dagger client:
```go
if testing.Short() {
    t.Skip("skipping integration test")
}
dag, err := dagger.Connect(ctx)
require.NoError(t, err)
defer dag.Close()
```

### 3. File Locking

Use the lock manager for Git operations:
```go
err := r.lockManager.WithLock(ctx, LockTypeNotes, func() error {
    // Git operation here
    return nil
})
```

### 4. Container State

Always save state after modifications:
```go
container = container.WithExec(cmd)
// Must update environment state!
if err := env.apply(ctx, container); err != nil {
    return err
}
```
